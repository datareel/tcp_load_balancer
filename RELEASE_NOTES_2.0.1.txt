DRLB 2.0.1 release notes
DRLB TCP load balancer, 11/18/2026 (not yet released)

OpenSSL on RHEL 8: two packages (same model as DRCM 1.49)
---------------------------------------------------------
* The 2.0 RHEL 8 RPM (drlb_server-2.0-1.el8) linked the RHEL 8 OpenSSL
  1.1.1k with nothing that said so or checked it. The RHEL 9 and RHEL 10
  2.0 RPMs were already on OpenSSL 3.5.
* RHEL 8 now has two packages, like DRCM 1.49. Install one of them:
  - drlb_server-2.0.1-1.el8: the RHEL 8 system OpenSSL 1.1.1, which Red
    Hat validated for FIPS 140. This is the FIPS build: classic TLS
    only, and the TLS groups, signature algorithms and ciphers follow
    the system crypto policy (update-crypto-policies). It is where
    "dnf upgrade" from 2.0 lands.
  - drlb_server-openssl35-2.0.1-1.el8: OpenSSL 3.5.9 LTS built in
    statically, with post-quantum TLS. It needs no OpenSSL package (no
    EPEL) and has no rpath. Not for FIPS mode: the built-in OpenSSL is
    not FIPS validated, and it does not read the system crypto policy
    (its OpenSSL config path is /opt/openssl-3.5/ssl, which is not
    installed). It provides drlb_server and conflicts with it; move a
    host between the two with
      dnf swap drlb_server drlb_server-openssl35-2.0.1-1.el8.x86_64.rpm
    (and back the same way). The config, keys and service state stay.
  OpenSSL security fixes for the openssl35 package mean a new DRLB
  build: rpm/build_openssl35.sh pins the OpenSSL version and SHA-256.
* Build checks:
  - Every build except the RHEL 8 FIPS build stops on OpenSSL headers
    older than 3.5 (src/tls.cpp), and the program stops at start on an
    older library. The FIPS build needs the explicit "make FIPS_BUILD=1"
    and allows OpenSSL 1.1.1 or later.
  - "make OPENSSL_PREFIX=/opt/openssl-3.5 OPENSSL_STATIC=1" links a
    static OpenSSL; rpm/build_openssl35.sh builds OpenSSL 3.5.9 from the
    official tarball with a pinned SHA-256 (same script and version as
    DRCM 1.49).
  - rpm/make_rpm_package.sh rhel8 | rhel8-openssl35 | rhel9 | rhel10
    checks each package: rhel8 must link libssl.so.1.1 and be a FIPS
    build, rhel8-openssl35 must have no libssl/libcrypto in NEEDED, no
    rpath, no OpenSSL requires and OpenSSL 3.5, rhel9/rhel10 must
    require libssl.so.3(OPENSSL_3.5.0).
  - drlb_server --version prints the OpenSSL it runs with, the flavor
    (system or static) and FIPS state.
  - The RPM build host is "datareel-build" (DRLB_BUILDHOST), and the
    script refuses an RPM that records another one.
  - CMake needs OpenSSL 3.5 (find_package(OpenSSL 3.5 REQUIRED)).
  - Optional: make OPENSSL_PKG=name builds against a pkg-config package
    such as the EPEL openssl3-devel. No package is shipped that way.
* drlb_server-openssl35 on a host in FIPS mode logs a warning at start
  that its built-in OpenSSL is not FIPS validated; use drlb_server there.
* Tested on a RHEL 8.10 host in FIPS mode: the FIPS build passes every
  suite (TLS 1.2/1.3 on P-256/P-384, RSA and ECDSA certificates, verified
  back ends; X25519, 3DES and ML-KEM refused).
* Backend certificate checks with no ssl_backend_ca_list_file also load
  /etc/pki/tls/certs/ca-bundle.crt, so the static OpenSSL (whose default
  paths are under /opt/openssl-3.5) still uses the RHEL trust store.

Post-quantum TLS
----------------
(RHEL 9, RHEL 10 and the RHEL 8 drlb_server-openssl35 package. The RHEL 8
FIPS build drlb_server has no post-quantum TLS: it logs that at start,
and ssl_groups and ssl_sigalgs are ignored there with a warning instead
of stopping the server.)
* Key exchange: DRLB now sets the TLS key exchange groups itself, with
  the hybrid post-quantum ML-KEM groups (FIPS 203) first:
  X25519MLKEM768, SecP256r1MLKEM768, SecP384r1MLKEM1024, then X25519,
  secp256r1, X448, secp384r1, secp521r1, ffdhe2048, ffdhe3072. The same
  list is used on the frontend and on TLS backends. The RHEL 8 and
  RHEL 9 crypto policies do not offer ML-KEM, so in 2.0 TLS on those
  releases used classical X25519 only. Classical clients and backends
  still connect (X25519 or P-256).
* The server prefers ML-KEM: a client that supports X25519MLKEM768 but
  sends only an X25519 key share is asked for an ML-KEM key share.
* Backend connections send X25519MLKEM768 and X25519 key shares, so a
  backend without ML-KEM still completes in one round trip.
* Certificates: ML-DSA (FIPS 204) certificates work on the frontend and
  on backends. The default signature algorithm list is mldsa65,
  mldsa87, mldsa44 plus the ECDSA, EdDSA, RSA-PSS and RSA PKCS#1
  algorithms of the RHEL DEFAULT policy. RSA and ECDSA certificates
  work as before. The log shows the certificate key type at start.
* ML-DSA certificates and clients: a client must also support ML-DSA to
  verify an ML-DSA server certificate. Clients that follow the RHEL 9
  DEFAULT crypto policy (and RHEL 8, and most browsers today) offer no
  ML-DSA signature algorithms and fail the handshake, so keep an RSA or
  ECDSA certificate on public frontends. Key exchange (ML-KEM) needs
  nothing from the certificate and works with any certificate type.
* New [SSLCONFIG] settings:
    ssl_groups   key exchange groups (OpenSSL 3.5 list syntax)
    ssl_sigalgs  signature algorithms
  Empty (default) uses the DRLB lists above. "system" keeps the system
  crypto policy lists. In FIPS mode both default to "system". A bad
  value is a config error.
* ssl_protocol = TLSv1_2 logs a warning: TLS 1.2 has no post-quantum
  key exchange. TLS (1.2 and 1.3, the default) and TLSv1_3 are fine.
* log_level = 4 logs the TLS version, cipher and key exchange group of
  every frontend and backend connection.

Documentation
-------------
* docs/SECURITY_DESIGN.md: the security design white paper (also
  https://datareel.com/drlb/security_design.php).
* AGENTS.md, with CLAUDE.md and GEMINI.md: the AI-assisted install,
  upgrade and support guide (also
  https://datareel.com/drlb/ai_assisted_guide.php). Human in the loop,
  never autonomous; written management approval and approved enterprise
  AI models first.
* Both are installed in /usr/share/doc/drlb by the RPMs.

Tests
-----
* New tests/pqc_tests.py (part of "make test"): ML-KEM groups on the
  frontend and backends, ML-KEM preference, classical fallback,
  ssl_groups and ssl_sigalgs settings, ML-DSA certificates on the
  frontend and backends, and the OpenSSL 3.5 link.

Unchanged
---------
Everything else in 2.0: settings, defaults, config files, the systemd
units and the drlb user.
