DRLB 2.2.0 beta 1 release notes
DRLB TCP load balancer, 11/20/2026

Port multiplexer (mode = MUX)
-----------------------------
* New mode = MUX in [LBSERVER]: drlb_server listens on many local TCP
  and UDP ports ([MUXPORT]), from any number of processes, and carries
  every connection and datagram over one TLS tunnel connection to a
  peer DRLB. The peer delivers each channel to its destination
  ([MUXDEST]): one host and port, or [LBNODE]s load balanced with
  LB_RR, LB_WEIGHTED, LB_DISTRIB or LB_ASSIGNED (assigned rules match
  the original client address on the other server).
* Both directions: each server can have [MUXPORT] and [MUXDEST]
  sections, so channels go either way over the same tunnel. One server
  connects ([MUXTUNNEL] remote_host, remote_port), the other accepts
  (mux_listen = 1 on port and listen_ip_addr).
* More tunnels: several [MUXTUNNEL] peers and tunnel_connections = N
  spread new streams round robin over every tunnel that is up and
  delivers the channel (fail over to a second peer); peer = NAME keeps
  a [MUXPORT] to one peer.
* TCP: per stream flow control (mux_stream_window, 256 KB), so a slow
  service only stops its own stream; fair scheduling of one frame per
  socket per turn; half close and resets carried; idle streams closed
  after timeout_secs when use_timeout = 1.
* UDP: one flow per client address and port with its own destination
  socket, datagram boundaries kept, flows end after mux_udp_idle_secs;
  datagrams are dropped and counted, not queued without limit, when the
  tunnel is congested.
* Security: mutual TLS by default with the 2.0.1 TLS settings
  (hybrid ML-KEM first on OpenSSL 3.5, the FIPS build on RHEL 8 FIPS
  hosts). New [SSLCONFIG] settings ssl_verify_client (default 1) and
  ssl_client_ca_list_file. mux_allowed_peers limits peers by name, and
  the name must be in the peer certificate. A config without
  [SSLCONFIG] is an error unless mux_allow_plain = 1, which prints and
  logs a WARNING at every start that the tunnel is not encrypted.
* Reconnect with backoff (mux_retry_secs doubling up to 60 seconds),
  keepalive (mux_keepalive_secs), GOAWAY on shutdown so the peer logs
  why the tunnel closed. While no tunnel is up, new TCP clients are
  held up to mux_hold_secs (default 10) and go through when a tunnel
  comes up, so a restart or a short outage does not refuse them; UDP
  datagrams are dropped.
* --check-config checks MUX configs: channel names, duplicate channels
  and ports, unknown nodes, nodes without weights for weighted
  schemes, ports without a tunnel, TLS or mux_allow_plain.
* Stats: one line per tunnel (state, streams, bytes, queue, round trip
  time), per [MUXPORT] and per [MUXDEST].
* Wire protocol DRMX version 1 (src/mux.cpp). Both servers need 2.2.
* Example configs mux_example_a.cfg and mux_example_b.cfg, and
  mux_replication_a.cfg and mux_replication_b.cfg (two packages'
  database replication over one tunnel port, 2073), and a pair for
  each use in "Why the port multiplexer": mux_consolidate_*,
  mux_firewall_*, mux_encrypt_*, mux_stdports_* and mux_vhost_*, in
  /usr/share/doc/drlb; "Port multiplexer" chapter in the user guide.
* One event loop thread (epoll) per MUX config; the load balancer code
  path (mode = LB, the default) is unchanged and every 2.0.1 config
  runs as before.

Measured on a 4 core test host with two DRLB processes and TLS 1.3
(X25519MLKEM768): about 2 Gbit/s of TCP each way through one tunnel,
8,000 concurrent streams, more than 50,000 UDP datagrams per second.

Tests
-----
* New tests/mux_tests.py (37 checks), run by make test: TCP and UDP
  channels both ways, LB_RR and LB_WEIGHTED channels, 300 concurrent
  streams, 64 MB throughput, a stalled stream does not block the
  others, half close, dead destination, UDP idle flows, stats,
  reconnect after the peer restarts, client certificate from another
  CA, peer name checks, malformed frames, config checks. Also clean
  under make asan.

Packaging
---------
* drlb_server-2.2.0-0.beta1 (RPM Release 0.beta1, so 2.2.0-1 will
  upgrade it). --version prints 2.2.0-beta1.
* Known limits of the beta: IPv4 only (as the load balancer); TLS to
  the destinations (ssl_encrypt_backend) is not used in MUX mode; each
  new stream on the delivering side uses a short lived connect thread.
